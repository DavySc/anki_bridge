# Spec: auth (module `auth`)

Status: BUILT. Part of [CAPABILITY-MAP.md](CAPABILITY-MAP.md).
Depends on: nothing. Required by: `deploy`.

## Objective

Only the owner can let Claude call the Anki tools. Today `server.py` has no
authentication, so the port must not be exposed. This module makes the server
its own single-user OAuth 2.1 authorization server and resource server, so Claude
(web, desktop, phone) can add it as a remote MCP connector and nobody else can
use it.

Success looks like: add the server URL as a custom connector in Claude, get sent
to a login page on my server, enter my secret once, and from then on tools work.
Any request without a valid token, or with a token I did not authorize, gets 401.

Non-goals: multi-user accounts, roles, external IdP, per-tool scopes, a UI
beyond one login form. Multi-user is not built, but the design keeps it cheap
(see "Multi-user seams").

## Tech Stack

- Python 3.13, `mcp>=2.2,<3` (installed 2.3.0), `MCPServer` with
  `auth=AuthSettings(...)` and `auth_server_provider=...`.
- The SDK already provides: discovery metadata, dynamic client registration,
  `/authorize`, `/token` (PKCE), `/revoke`, bearer middleware. This module only
  supplies the provider (storage + the consent step), not the protocol.
- Storage: SQLite file next to the collection (stdlib `sqlite3`). No new
  dependencies.

## Design

- `auth.py`: `OwnerProvider` implementing `OAuthAuthorizationServerProvider`.
  - `register_client` / `get_client`: persist dynamically registered clients.
  - `authorize`: redirect to `/login?req=<opaque id>`; the pending request is
    stored server-side, expires in 10 minutes, single use.
  - `/login` (custom route, unauthenticated, via `@mcp.custom_route`): GET shows a
    form, POST checks the owner secret in constant time, then issues an
    authorization code and redirects to the client's `redirect_uri`.
  - Auth codes: single use, 5 min expiry, bound to client, redirect_uri and PKCE
    challenge.
  - Access tokens: opaque random (>=256 bit), stored hashed (SHA-256), 1 hour.
  - Refresh tokens: opaque, hashed, rotated on use, 30 days. Reuse of a rotated
    token revokes that client's grant.
  - `revoke`: enabled.
- Owner secret: `OWNER_SECRET_HASH` env var (argon2/scrypt hash, generated by a
  helper `python auth.py hash`), never the plaintext in env or repo.
- Login brute-force limit: 5 failed attempts per 15 minutes per IP (25 across all IPs), then 429.
  Per-process in-memory counter is enough (single process).
- `server.py` wires `AuthSettings(issuer_url=PUBLIC_URL, resource_server_url=
  PUBLIC_URL/mcp, validate_token_resource=True, client_registration_options=
  enabled, revocation_options=enabled)`.
- Auth is mandatory outside tests: if `PUBLIC_URL` or `OWNER_SECRET_HASH` is
  missing the server refuses to start, unless `ALLOW_INSECURE_NO_AUTH=1` is set
  AND the bind host is loopback. No silent unauthenticated mode.

## Multi-user seams

Built now, because they are nearly free; the rest of multi-user is not built.

- `subject` is stored on pending requests, codes, access and refresh tokens, and
  returned in the SDK's `subject` field. Constant `owner` today.
- `Authenticator` interface: `authenticate(credentials) -> subject | None`.
  `OwnerAuthenticator` checks the one scrypt secret. A later `UserTable`
  authenticator replaces it without touching the OAuth code. The login form has
  a hidden/optional username field that is ignored today.
- Rate limiter keys on the client IP plus a global bucket, never on the claimed
  username (the attacker chooses it). A later multi-user authenticator may add
  the username as an extra key, not a replacement.
- Revocation and reuse detection are scoped to the grant (one login: its code and
  every token issued from it), which carries the subject and client. Reusing a
  code or a rotated refresh token revokes that grant; revoking either token ends it.
- With `resource_url` set, `/authorize` rejects other resources (`invalid_target`)
  and a missing resource defaults to ours, so tokens always carry our audience.
- `server.py` resolves the caller with `bridge_for(subject)` (subject from
  `get_access_token()`), not a module-level global. Today it returns the one
  Bridge. If `get_access_token()` is None under auth, the tool fails closed.
- Data layout `data/<subject>/...`; `ANKI_COLLECTION` overrides for the owner.

## Code Style

Match `core.py`: type hints, `from __future__ import annotations`, short
docstrings that say why, errors as messages meant for the caller, no MCP types
leaking into `core.py`.

    class OwnerProvider:
        """Single-user OAuth provider. Storage is SQLite; secrets are hashed."""

        async def load_access_token(self, token: str) -> AccessToken | None:
            row = self._db.execute(
                "SELECT client_id, scopes, expires_at FROM access_tokens WHERE hash = ?",
                (_sha256(token),),
            ).fetchone()
            ...

## Testing Strategy

pytest, no network. Drive the provider and the Starlette app in-process
(`starlette.testclient`).

- Unit: token hashing and expiry, code single-use, refresh rotation and reuse
  revocation, PKCE mismatch rejected, redirect_uri mismatch rejected, rate limit.
- Flow: register -> authorize -> login (wrong then right secret) -> token ->
  call `list_decks` with bearer -> refresh -> revoke -> call fails.
- Negative: no header, malformed header, expired, revoked, token for another
  resource (audience) all return 401; tool code is never reached.
- Startup: missing config refuses to start; insecure flag refused on non-loopback.
- Manual (once, after tests): real Claude connector against a tunnelled or
  deployed instance. Recorded as a checkbox, since it needs `deploy`'s HTTPS.

## Boundaries

- Always: store only hashes of secrets/tokens; compare secrets in constant time;
  expire and single-use codes; log auth failures without logging secrets or
  tokens; run the full pytest suite before committing.
- Ask first: adding a dependency (e.g. argon2-cffi; stdlib `hashlib.scrypt` is the
  default), changing token lifetimes, adding scopes, changing the DB location.
- Never: add a module-level global Bridge or hardcode the string `owner` outside the single place that defines the owner subject; commit or log the owner secret or any token; add a bypass header or
  default password; touch `core.py` behaviour; weaken the `approved_by_user`
  guard (auth is not approval; they are separate layers).

## Success Criteria

- [x] Unauthenticated `POST /mcp` returns 401 with a `WWW-Authenticate` header
      pointing at the protected-resource metadata.
- [x] `/.well-known/oauth-authorization-server` and
      `/.well-known/oauth-protected-resource` are served with the public URL.
- [x] Full flow test passes: register, authorize, login, token, tool call,
      refresh, revoke.
- [x] Wrong owner secret never yields a code; 6th attempt in 15 min is 429.
- [x] Server refuses to start without auth config (and with the insecure flag on
      a non-loopback host).
- [x] DB contains no plaintext tokens, codes or owner secret and no client secret (asserted in tests). Client secrets are derived from a server key, which is derived from the owner secret hash, and recomputed on demand.
- [x] Tokens issued to a second subject (test-only authenticator) resolve to a different `bridge_for` result and cannot read or revoke the owner's tokens.
- [x] A tool call with no subject in context fails closed under auth.
- [x] All existing `test_core.py` tests still pass unchanged.
- [x] README "Status" updated; GOALS.md "Auth ... Still to be built" updated.

## Findings during build

- mcp 2.x hides the text of ordinary exceptions from the model; only `ToolError`
  text is shown. `server.py` wraps tools with `surfaced` so `BridgeError`
  messages ("Not approved...", validation errors) reach Claude. Before this the
  model only saw "Error executing tool ...".
- Behind Caddy, the SDK's DNS-rebinding check rejects the public Host header
  unless allowed; `transport_security()` allows the PUBLIC_URL host.

## Open Questions

1. Does the Claude custom-connector flow (especially the phone app) accept
   dynamic client registration against this server, or does it need a
   pre-registered client id? Spec assumes DCR works; `deploy` verifies.
2. Does Claude's callback URL need to be allow-listed? If DCR works, I'd accept
   only `https://claude.ai/...` and `https://claude.com/...` redirect URIs plus
   loopback for Inspector. Confirm the exact URLs when testing.
3. Is `hashlib.scrypt` (stdlib) acceptable for the owner secret, to avoid a new
   dependency? Recommended: yes.
4. Token lifetimes (1 h access, 30 d refresh): fine for a single-user phone use?
5. Multi-user: confirmed out of scope, seams only (see above).
6. Should the login page also require a TOTP code? Recommended: no for v1; the
   scrypt secret plus rate limit is enough for a single-user tool, and it can be
   added later.
